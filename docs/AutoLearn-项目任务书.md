## 1. 项目目标

构建一套**基于视觉模型的页面自动化系统**（v0.2.0：只使用模型读页面），实现「感知 → 求解 → 决策 → 执行 → 校验」的完整闭环，并支持人工确认的半自动模式。

> **⚠ 2026-09-27 修订**：原文为「首要（也是 T0–M6 阶段唯一）目标环境为**自建靶场**，
> 真实平台适配留到扩展阶段」。**这一条与用户意图不符，已作废**。
>
> 修正后的目标环境是：**抓取电脑上正在运行的网页**（用户自己开着的浏览器标签页），
> 由用户从列表中勾选要抓的目标，再交给模型（视觉）识别。
> 自建靶场**降级为测试专用**：它仍是唯一的回归基础设施，但不再出现在产品界面上。
>
> 落地为 **P11 目标采集层**，接口契约见 `docs/CHANGELOG-interface.md §P11`。
> 里程碑表（§5）中 M0 的靶场相关条目同样按此重读。

核心技术路线：Playwright 驱动浏览器 + 多模态模型读题 + 原生结构化输出 + 规则化动作编排。核心判断：**瓶颈在执行层，不在识别层**，工程量投在 `Actuator` / `Verifier` 而非 prompt 调优。

> **v0.2.0 对这条判断的补充**：执行层仍是瓶颈，但**读题侧必须单独重视** —— 它是全链路
> 唯一「错了也不报错」的环节。提示词纪律（只读不答 / 坐标归一化 / 找不到就留空）与
> 读题质量门禁因此属于工程量，不是可选的调优。

**题目通道只有一条：视觉。** 用户在运行配置里没有可选的通道、优先级或模式
（0.1.0 的 `DOM 优先 / 模型优先` 与 `dom-only / vision-only` 调试开关已全部删除）。
选择权只剩「用哪套模型」，见 §3.2。

**模型 API 配置不是本项目的任何前置条件。** 软件交付后由用户在软件内自行添加，配专门的引导提示与独立 UI 界面（见 §3）。

## 2. 应用场景

### 2.1 场景 A — 网课自动化

**流程**：定位课程分集列表 → 进入某一集 → 点击播放 → 校验进入播放态 → 播放过程中监听弹题打断 → 播放结束 → 点击下一集 → 直到分集列表完成。

**关键环节与技术要点**：

| 环节 | 技术要点 |
|------|---------|
| 播放状态感知 | **不能靠元素"可见"判断**。必须读媒体状态：`paused` / `ended` / `currentTime` / `duration`，并监听 `timeupdate` / `ended` / `pause` 事件 |
| 播放启动校验 | 点击播放按钮后**回读 `paused === false`**，与 §4 第 5 项回读校验复用同一套机制 |
| 弹题打断处理 | 属于**嵌套中断**，不是线性流程。播放中被弹题打断时需压栈、暂停播放、处理弹题、弹栈恢复播放 |
| 进度推进 | `ended` 事件触发后点击下一集，并**校验集数 / 进度确实变化**，防止点了没生效 |
| 断点续跑 | 记录 `vid` + 已播放位置，中断后可从该位置恢复 |

### 2.2 场景 B — 刷题自动化

**流程**：感知题目（截视口图 + 模型读题）→ 求解 → 决策动作序列 → 按坐标执行 → **截图差分校验** → 提交 → 结果确认 → 点击下一题 → 直到题量上限或全部完成。

该场景由 M0–M4 完整覆盖，无需新增架构能力。

### 2.3 场景对架构的增量要求

场景 A 引入了「多任务类型」与「嵌套中断」两个新维度，现有单线性题目队列不足以承载：

| # | 增量 | 说明 |
|---|------|------|
| 1 | **任务类型分派** | Orchestrator 从「题目单一队列」升级为**多任务类型队列**（`video` / `quiz`），支持按配置组合任务序列 |
| 2 | **中断-恢复机制** | 引入**任务栈**。弹题到来时压栈并挂起当前视频任务，弹题处理完毕后弹栈恢复，而不是中断整个流程 |
| 3 | **视频标识 `vid`** | 与 `qid` 并列的独立标识：`sha1(课程ID + 集数 + 标题)[:16]`。视频不属于题目，不能复用 `qid` |
| 4 | **状态机扩展** | 新增媒体态：`playing` / `paused` / `interrupted` / `resumed`，与既有 9 态题目状态机并存 |
| 5 | **媒体动作** | Actuator 新增 `PlayMedia` / `PauseMedia` / `SeekMedia`，纳入既有六级升级阶梯 |
| 6 | **进度断言** | Verifier 新增：`paused` 回读一致、`currentTime` 单调推进、分集索引变化 |

## 3. 运行期配置与软件内引导

**原则**：模型 API 配置**不由开发者预置，也不是任何阶段的前置条件**。软件落地后，由用户在软件内自行添加。任务书中不出现「申请 / 准备 API Key」类前置任务。

### 3.1 题目通道：只有视觉一条（v0.2.0）

**这一节在 0.1.0 是「通道优先级（用户可选）」，整节已重写。**

0.1.0 让用户在运行配置里选「`DOM 优先`（DOM → 网络 → 视觉）或 `模型优先`
（视觉 → DOM → 网络）」，还允许叠加 `dom-only` / `vision-only` 调试开关。
**v0.2.0 把这套选择整体删除**：`ProbeOrder` / `ProbeMode` / `PROBE_CHAINS` /
`CAPABILITIES` 与 `core/targets.modes_for()` 都不存在了，向导里的「通道模式」下拉也没了。

现在的唯一读题路径：

```
截当前视口图（page.screenshot()，禁用 full_page）
        │
        ▼
视觉组模型：返回题干 + 选项文本 + 每个选项的归一化包围框 (0..1)
        │  同时声明「题面是否被截断 / 我是否拿不准」
        ▼
gate_read_result()：clipped 或 uncertain 非空 → 拦下并带原因暂停问人
        │ 放行
        ▼
解题组模型作答 → norm_box_center() 换算成视口 CSS 像素 → 点击 → 截图差分校验
```

- 通道只剩一条，**没有「选错模式就必然失败」这回事了**；敲定的东西只有一个：
  用哪套模型（见 §3.2）。
- `core/config.py::active_probe_chain(cfg)` 恒返回 `[ProbeName.VISION]`；
  `ProbeName` 只剩 `VISION` 与 `MEDIA`，其中 `MEDIA` **不在题目探针链里**。
- **目标类型不再决定「信哪条通道」**：`TargetKind`（浏览器页 / 原生窗口）现在只决定
  「怎么拿到画面」——浏览器页走 CDP 附加、原生窗口走 Win32 截图。原先那张
  「目标类型 → 可用通道」能力矩阵随之删除，界面也不需要再把某个通道置灰。
- **`supports_vision` 成为硬前置**：0.1.0 里只有「模型优先」才强制要求视觉模型，
  现在**任何**运行都必须有 —— 没有模型就完全跑不了（不存在退化成 DOM 通道的活路）。
  未选时预检直接拒绝并给出引导码，不是静默失败。

**两个必须写清的代价**（0.1.0 没有它们，因为那时有一条零成本的 DOM 读题路）：

| 代价 | 说明 | 对应设计 |
|------|------|---------|
| **每题一次模型调用** | 读题本身就要发图；锚点站点的「零模型调用读题」不复存在 | 默认**不复算**（`RunConfig.recalculate = False`、`sample_n = 1` → 每题只核对一次、取第一次答案）；图像体积（`vision:bytes=`）是唯一还有优化价值的成本项 |
| **读错题在下游不可见** | 模型返回结构完好的 JSON、没有错误信号；少一个负号、漏一个指数、被视口截掉半行，都会算出一个「看起来正常」的错答案并按坐标点到真实页面上 | 读题质量门禁（见 §4 末「读题质量门禁」）、开局裁决（`derive_plan`）、收尾确认（看 `page.completed`） |

**校验侧的诚实边界**：题目侧现在只有**截图差分**（点前后比选项区域像素，
`VerifyKind.SCREENSHOT_DIFF`）。它能证明的只是「点下去之后那块像素变了」，
**不能**证明「选中的就是我想要的那一项」——动画、hover、toast 都会让它变化。
0.1.0 的 DOM 回读（读 `checked` / `aria-checked`）能直接断言输入框状态，
那条判据随 DOM 通道一起删除了。所以自动校验只能覆盖「点到了东西」，
「读对了没有」必须靠第 9 项的门禁把不确定性顶到人面前。

### 3.2 模型配置由用户自行添加

#### 专用引导提示（硬性）

- **首次运行**（无任何配置）时，UI 不报错、不阻塞运行，而是展示**引导卡片**：去哪注册、能拿到什么免费额度、需要填哪几个字段、如何验证
- 模型配置区的**空状态** / **鉴权失败** / **模型名不存在** / **限流** 四类情形，各自有独立文案与下一步动作，不共用一句泛化错误
- 用户未添加任何配置时，系统自动落到 `MockProvider`，全链路仍可跑通（见 M2-1）

#### 专用 UI 界面

- 模型配置为**独立面板**，支持多套配置的**新增 / 编辑 / 删除 / 排序**（排序即降级链）
- 表单字段、预设模板、[测试连接] 的行为见 M2-6
- 密钥仅保存不回显，见 §7.2

#### 与里程碑的关系

- **T0 / M0 完全不涉及模型配置**：M0 验收要求零模型调用
- 用户在 M1-4b / M2 阶段自行添加配置后，才能跑真实模型数据与 M2 闸门
- 若 M2 期间用户仍未添加配置，**闸门判定顺延**；期间用 MockProvider 验收投票逻辑与 UI 链路，但**不得作为闸门依据**

## 4. 前置任务 T0：关键定义冻结

**投入：0.5 人日 | 无依赖 | 阻塞全部后续里程碑**

定义未冻结即动手，会在 M3 / M4 阶段产生**错答与重复提交**类缺陷。

| # | 定义项 | 内容要求 | 冻结产物 |
|---|--------|---------|---------|
| 1 | `qid` 算法 | `sha1(NFKC归一化题干 + "\|" + "\|".join(sorted(归一化选项)))[:16]`；**不含答案**；选项排序后参与哈希；NFKC 归一化统一全角半角与标点 | `core/qid.py` |
| 2 | 状态机 | 9 态：`pending` / `perceived` / `solved` / `pending_confirm` / `applied` / `submitted` / `verified` / `failed` / `skipped`，附完整转移表；**`submitted` 为唯一危险态**，续跑时只做结果回读、绝不重新点击；`submitted` 之后确认按钮置灰 | `core/states.py` |
| 3 | Tier 升级条件 | `agreement ≥ 0.8` → 直接采用、不调 Tier2；`< 0.8` → 交 Tier2 复算；带图 / Canvas / 题干截断 → 直接 Tier2；Tier1 与 Tier2 多数解不同 → 标记 `⚠复核` 且必停；两者均低于门限 → 标记 `⚠复核` + 留截图 + 暂停。**Tier2 必须投票，≥3 次** | `RunConfig` 常量 |
| 4 | 自指选项白名单 | 正则覆盖「以上 / 上述 / 以下 / 下列 / 都[对正确错] / 均[对正确错] / 全[部不对] / 前者 / 后者 / (A)和 / A和C」。**2026-09-30 起根本不再打乱选项**（标号逐字等于页面标号），自指检测降级为**风险标注**（`allows_shuffle` / `question_has_self_ref`），只进留痕、不改变呈现顺序 | `solve/solver.py` 常量 |
| 5 | 回读不一致处置 | 「点下去了没有」是**三态**判定（`act/verifier.py::region_change_state`）：`mad ≥ 2.0` → `changed`、`≥ 0.05` → `weak`、否则 `none`；`changed` / `weak` 都算点到。处置按**落点**分：落在墨迹（`ink_centroid`）上判 `none` → **绝不重点**（照旧收工，`readback` 记 `no_change_on_ink:…`）；几何兜底落点判 `none` → 换下一个候选点（换点前先重测）；候选全 `none` → 暂停 + 截图 + 记 `failed`。**禁止用 `assert`，禁止静默继续**。题目侧「一致」判据是**截图差分**（点前后选项区域像素），不再读 DOM 属性 | `act/verifier.py` + `act/actuator.py` |
| 6 | M2 止损数字 | 单选 Top-1 ≥ 0.85；多选完全匹配 ≥ 0.75；采样一致率 ≥0.8 的题占比 ≥ 0.80 | `RunConfig` 常量 |
| 7 | **`vid` 视频标识** | `sha1(课程ID + 集数 + 标题)[:16]`；仅用于视频任务，**不复用 `qid`**；参与断点续跑与去重 | `core/vid.py` |
| 8 | **任务类型与中断模型** | 任务类型枚举 `video` / `quiz`；任务栈结构定义并**落盘 SQLite**（压栈 / 弹栈 / 挂起 / 恢复）；媒体态与题目态的衔接规则 | `core/tasks.py` |

**验收标准**：

- [ ] 8 项全部落为**代码常量或配置项**
- [ ] `make_qid()` 通过「打乱选项后 qid 不变」单测
- [ ] 状态机转移表通过「`submitted` 态续跑不重复提交」单测
- [ ] 自指检测通过「含自指选项的题不被乱序」单测
- [ ] 任务栈通过「视频播放中弹题 → 弹题完成 → 恢复原视频」单测

### v0.2.0 增补契约：读题质量门禁（不属于 T0 那 8 项，但同样是冻结契约）

T0 的 8 项是 0.1.0 冻结的；下面这条是 P15 引入、v0.2.0 起成为**唯一**质量出口的契约。
它替代了 0.1.0 里「DOM 通道读不出就换通道」那套兜底 —— 现在没有第二条通道可换，
读题的不确定性只能由模型自己声明、由门禁拦住。

| 定义项 | 内容要求 | 冻结产物 |
|--------|---------|---------|
| 视觉观测格式 | 视觉组**只做观测**：一次回两块 `{"page": {...}, "questions": [...], "more_below", "note"}`。`page` 字段：`progress` / `total` / `current` / `next_control{box,label}` / `card{box,cols,rows,current_box,next_box}` / `submit{box,scope}` / `completed`（`all_done` \| `not_done` \| `unknown`）/ `scrolling` / `reason`。**`page` 里只报告「有什么」，不报告「该怎么办」** | `core/models.py::PageView` / `ReadBatch` |
| 读题质量字段 | 每道题的 `ReadResult` 带 `clipped` / `uncertain` / `more_below` / `unsupported_qtype` / `note`。模型**主动声明**题面被截断或自己拿不准 | `core/models.py::ReadResult` |
| 门禁判据 | `gate_read_result(result) -> (放行?, 原因码)`：`clipped` 非空 → `vision_incomplete`；`uncertain` 非空 → `vision_uncertain`；**拦下就带这个具体原因暂停问人，不放行、不硬答**。`more_below` 单独不拦（多题同页是正常形态）；**「这一屏没有提交按钮」不归门禁管**（提交时机由开局裁决定死，见下一行） | `solve/reader.py::gate_read_result` |
| 开局裁决（取代「开局标定」） | 开局那一次读图就把四件事定死：①推进方式**恰好一种**（`card` 点答题卡题号 / `click` 点固定控件 / `scroll` 向下滚动 / `swipe` 滑动，优先级 `core.advance_library.PLAN_PREFERENCE = (CARD, CLICK, SCROLL, SWIPE)`）②推进几何（控件框 `control_box`，或答题卡的 `card_origin` / `card_step` / `card_anchor`）③提交范围（`PAPER` 整卷 / `QUESTION` 每题）④总题数。**此后不再**每题重问模型「下一题在哪」、**不再换招**、**不再**「滚到顶重读一次」 | `core/run_plan.py::derive_plan` → `core/models.py::RunPlan` |
| 推不动就停 | 按方案推不动 → 请视觉组确认「是不是全部完成了」（看同一份固定格式里的 `page.completed`）：`all_done` 才干净收工，否则 `ErrorCode.ADVANCE_FAILED` 停下等人。推进后读到的题号与方案预期不符 → 同样按 `advance_failed` 停下。**绝不静默跳过** | `core/orchestrator.py::_settle_end` |

**为什么拦得这么狠（非空就拦，不做轻重分级）**：读题是全链路唯一「错了也不报错」的环节，
能自己承认「这里我没把握」的模型给出的信号恰恰最不该被忽略；拦截的代价只是停下来问人，
放行的代价是一次静默的错误作答。两侧代价不对称。

### M5 — 网课自动化场景

**依赖**：M4 ｜ **工作量**：4~5 人日

复用 M0–M4 的感知 / 求解 / 执行 / 校验层，新增任务调度与中断恢复能力。

| 编号 | 任务 | 交付物 |
|------|------|--------|
| M5-1 | 多任务类型队列 | `core/tasks.py` — 任务类型枚举 `video` / `quiz`，按配置组装的混合任务序列 |
| M5-2 | 任务栈与中断恢复 | 弹题到来 → 挂起视频任务并压栈 → 处理弹题 → 弹栈并恢复播放。挂起期间**必须显式暂停媒体**；恢复前回读 `currentTime` 未越界。**恢复语义**：栈落盘 SQLite，进程重启后**栈顶优先**，被挂起的视频以 `paused` 态重建、不自动续播。**优先级**：`ended` 与弹题同刻到达时 `ended` 优先——该集视为已完成，弹题处理完直接推进下一集，不恢复播放 |
| M5-3 | 播放控制与校验 | 点击播放 → 回读 `paused === false`；点击下一集 → 回读分集索引变化。校验失败按 T0 第 5 项处置 |
| M5-4 | 播放结束推进 | 监听 `ended` 事件触发下一集；同时兜底轮询 `currentTime >= duration`，防止事件丢失 |
| M5-5 | 断点续跑 | 记录 `vid` + 已播放位置，中断后从该位置恢复，不重播已完成的集 |
| M5-6 | UI 适配 | 任务列表同时呈现「分集进度」与「弹题状态」，区分展示媒体态与题目态 |

**进度断言量化**（Verifier 实现依据，无数字则无法验收）：

| 断言 | 判据 |
|------|------|
| 播放态推进 | 采样窗口 3s 内 `ΔcurrentTime ≥ 1.0s` |
| 暂停态静止 | 采样窗口 3s 内 `ΔcurrentTime ≤ 0.2s` |
| 恢复位置连续 | 恢复时 `\|currentTime − 挂起时 currentTime\| ≤ 2s` 且 `currentTime < duration` |
| 分集索引变化 | 点击下一集后，索引严格 +1 |

**验收标准**：

- [ ] 靶场中连续播完全部分集，自动推进无人工干预
- [ ] 弹题打断时**视频被显式暂停**，弹题处理完成后恢复播放且位置连续
- [ ] 播放结束事件丢失时，轮询兜底仍能推进下一集
- [ ] `ended` 与弹题同刻到达时按优先级正确推进，不重复播放该集
- [ ] 在弹题处理中途杀进程，续跑后栈顶任务优先恢复、视频以暂停态重建
- [ ] 中断后可断点续跑，不重播已完成的集
- [ ] 全部动作留痕，`level_used` 与媒体态切换有记录

### 2026-09-30 收口

用户对上一版给了四条判词，逐条对应到改动（施工图口径见《AutoLearn 实施规划书》§10）。

1. **「下一题处理仍然存在严重问题 → 程序开始运行时需要有一套判断逻辑，一旦判定好后续全部按它执行」**
   新增 `core/run_plan.py::derive_plan(batch, *, batch_size=0) -> RunPlan`：开局读图那一次就把四件事
   定死 —— ①推进方式**恰好一种**（`CARD` 点答题卡题号 / `CLICK` 点固定控件 / `SCROLL` 向下滚动 /
   `SWIPE` 滑动，优先级 `core.advance_library.PLAN_PREFERENCE`）②推进几何 ③提交范围
   （`PAPER` 整卷 / `QUESTION` 每题）④总题数。此后**不再**每题重问模型「下一题在哪」、
   **不再换招**（点击 → 滚动 → 滑动那套阶梯已整条删除）、**不再**「滚到顶重读一次」、
   **不再**因为「这一屏没有提交按钮」中途暂停。
   *历史事故*：旧 `advance_scroll` 一路滚到上限（0.8 屏 × 6 = **4.8 屏**），题号从第 3 题
   **跳到第 16 题**，中间 13 道被静默跳过 —— 现在滚动是「滚一步 → 读一屏 → 确认新题真的进来」，
   推不动就停。另一处：真机 `logs/10ca5ee8c89e` 里 44 题的卷子做到第 16 题，因「这一屏没有
   提交按钮」停在 `vision_no_submit_box` —— 现在提交范围由开局裁决定死，**中途不会**再因此暂停
   （该暂停码只剩「整卷范围跑完、要交卷时画面上找不到提交按钮」这一处，且提示用户手动点一次）。
   推不动时的处置：`_settle_end` → 请视觉组确认「是不是全部完成了」→ 确认才收工，否则
   `advance_failed` 停下等人；推进后读到的题号与方案预期不符（`_expected_number_ok`）同样停下，
   **绝不静默跳过**。答题卡落点是纯算术（`grid_geometry` / `card_cell_box`，网格**按行换行**、
   容差 `CARD_GRID_TOLERANCE = 0.10`），算不出来返回 `None` → **绝不点**。
2. **「视觉组模型的任务就是解读照片，将照片翻译成固定格式，解题组模型严禁拿到非文本输入」**
   视觉组（`prompts/00-共享契约.md` + `prompts/10-视觉组.md` → `solve/reader.READ_SYSTEM_PROMPT`）
   **只做观测**，一次回两块 `{"page": {...}, "questions": [...], "more_below", "note"}`；`page` 里
   只报告「有什么」，不报告「该怎么办」。解题组（`prompts/20-解题组.md` / `solve/solver.py`）
   **只吃文本**：请求里 `images` 恒为空；选项标号就是**页面标号**（可能不连续，如 A、B、D），
   **不再打乱选项**；输出多一个 `confidence`（空作答写 0，不许省略）。交接物 = 那一份固定格式本身。
   *历史事故*：读题时代「打乱选项」导致标号串位 —— 模型答 `D`、程序按位置映射落回 `C`，
   而错误从输出上完全看不出来（真机 `logs/10ca5ee8c89e/.../solve.json` 现场；视觉组给的非连续
   标号 `A, B, D` 会把位置字母彻底打乱）。现在标号逐字等于页面标号，自指检测只剩风险标注。
3. **「置信度系统也存在 bug：不使用复算系统则不存在置信度系统；不开启复算时存在模型无法解题的情况」**
   解题组自报 `confidence`，解析认 `0.8` / `"0.8"` / `"80%"`，越界夹到 `[0,1]`，空作答写 0。
   **不复算**（`sample_n == 1`）用自报值：低于 `guards.confidence_review_min`（默认 0.5）→
   标 `⚠复核`（理由「自报置信度低于门限」）并停下请人复核；模型没报 → 回到一致率（单样本恒 1.0）。
   **开复算**（`sample_n > 1`）用多数票占比，自报值不参与。**不可用的单次回复**（无 content /
   解析不出 / 标号越界 / provider 报错）是**请求失败**，走**有界重发**
   （`solve/solver.SAMPLE_RETRY_MAX = 2`，每条采样项最多 3 次请求），**不是**复算；
   **显式空作答是模型的结论**，不重发。`recalculated` 仍表示「是否开了复算」。
4. **「动作回读不一致判断逻辑存在问题：点击正确却判断错误，导致胡乱操作」**
   `act/verifier.py::region_change_state(mad)` 三态：`changed`（`mad ≥ REGION_CHANGE_MIN_MAD` = 2.0）
   / `weak`（`≥ REGION_CHANGE_WEAK_MAD` = 0.05）/ `none`；`verify_region_changed` 的
   `ok = state in {"changed", "weak"}`，`actual` 形如 `region_mad=0.31 state=weak`。
   `act/actuator.py::select_option` 的处置表按**落点**分：`ink_centroid` 落点 → `changed` / `weak`
   成功收工；判 `none` → **绝不重点**（`ok=True`，`readback` 记 `no_change_on_ink:…`）；
   几何兜底落点判 `none` → 换下一个候选点（换点前先重测）；全部候选都 `none` → `_exhausted`
   （`ok=False` + 截图 + pause）。
   *历史事故*：`region_mad=0.00` 时点在行尾空白、`region_mad=0.06` 时点了被禁用的交卷按钮 ——
   两次都是「点对了却被判成没点中，于是同一个框里再点 1~3 个候选点」造成的误点。
   现在 0.05 以上的轻微变化不再算「没变」，墨迹落点上的 `none` 一律不再重点。

**同一批里顺手补掉的四个真 bug**（都由这一批的测试逼出来，属于上面四条的边角）：

- **开局那一次读图曾经丢掉首屏第 1 题**：`_read_question_by_vision` 把同屏**其余**题入队、
  把第一道**返回**给调用方，而 `_plan_run` 没人接返回值，主循环又先取队列 ——
  「一屏多题」时首屏第 1 题**静默跳过**，单题屏被**读第二遍**。现在 `_plan_run` 把它
  `insert(0, …)` 放回队首（与 `_scroll_reveal_next` 既有约定一致）。
- **整卷提交后其余题停在 `applied`（不是终态）**：整卷只有一次提交动作，回读只挂在
  「最后作答的那道题」上；续跑时 `applied` 会被**重做**，多选题上重新点选项 =
  把刚选上的勾**取消**。现在提交确认后 `_settle_paper_batch()` 把这一轮其余 `applied` 的题
  按 `applied → submitted → verified`（状态机里 `applied` **没有**直达 `verified` 的边）
  一并推终态；**提交失败/暂停时不推**。
- **「只有 page 观测、没有题目」的开局屏曾经拿不到方案**（观测被丢在「至少一题过门禁」之后）；
- **提交框的第三个来源 `_last_submit`**（最近一次读图看到的框）：关掉开局判定
  （`guards.advance_calibrate=False`）+ 每题提交，原先**必然** `vision_no_submit_box`。
  现在按范围排序 `PAPER → [方案, 收尾, 最近]`、`QUESTION → [方案, 最近, 收尾]`，
  **每一对框与尺寸永远同源**。

### 尚未闭环的缺口

> **v0.2.0 让原第 1 项大幅缩小、第 2 项性质改变**，故本节重写（原文见文末引述）。

1. **真实站点适配向导（范围已大幅缩小）**：0.1.0 这里写的是「让用户在真实题目页上依次
   点选题干 / 选项 / 提交 / 结果 / 题型五个位置，生成 `selectors.yaml`」——
   **题目侧这部分缺口在 v0.2.0 直接消失**：题目不再需要任何选择器，模型看一眼页面就够了，
   而「知道抓到的是题干还是提交按钮」这个真正的难点本来就只有模型能解决。
   仍然需要向导的是**媒体侧**：真实网课页的 `<video>` / 分集列表 / 下一集按钮 / 弹题面板
   仍要靠 `selectors_media.yaml` 里的锚点定位，所以「点选生成媒体锚点」这件事还留着 ——
   但范围和难度都比原来的题目五锚点小得多。
2. **`DESKTOP_WINDOW` 采集实现**（原生窗口 + 视觉模型 + 系统级输入）。
   P11 只交付了枚举与护栏。**v0.2.0 起性质变了**：目标类型只决定「怎么拿到画面」，
   题目侧的「截图 → 模型 → 按坐标点」对所有目标都是同一条链路，
   原先用来拒绝桌面窗口的错误码 `TARGET_CHANNEL_UNSUPPORTED` 已删除
   （目标接不上统一记 `ErrorCode.TARGET_UNAVAILABLE`）。剩下的是采集与坐标换算的真机实测。
3. §4 的 M2 闸门指标仍未在真实模型上跑出（与上述两项互不阻塞）。
