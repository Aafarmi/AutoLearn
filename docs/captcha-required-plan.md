# Captcha Required 人工验证方案

日期：2026-10-25。本文记录验证码人工处理的完整方案；目前已实施验证码识别、停止当前运行、弹出提示和用户手动重试，同时保留参数说明与推荐值页面。

当前实施范围（2026-10-25）：捕获 `Captcha Required` 后停止当前课程运行并在 AutoLearn 弹出说明；用户自行打开智慧树网页登录并验证，之后回到详情页手动重试。不自动打开、嵌入或代理验证码页面，也不承诺原进程自动续跑。网页登录结果可能不与 AutoLearn 的 HTTP 请求会话共享；若重试仍触发验证码，建议重新扫码登录。完整的同会话暂停/续跑方案仍需真实挑战样本证明会话关联后再评估。

## 1. 已核实的现状

- `providers/zhihuishu/vendor/fuckZHS/fucker.py` 的 `zhidaoQuery()` 将上游响应码 `-12` 转为 `CaptchaException`。共享课循环捕获后输出 `Captcha required` 并返回，异常可能不会到达桥接层的外层捕获。
- 上游密码登录另有 `-4` 分支，含义是多次无效尝试后要求验证码。它与学习过程中的 `-12` 应区分；AutoLearn 当前主要采用二维码登录。
- 上游类有推送调用，但 `bridge.py` 创建实例时没有配置推送 token，因此不能把它视为当前 WebUI 已具备的通知能力。
- 现有 `protocol.py` 没有验证码事件；`domain.py` 没有等待验证状态；前端没有验证入口。现有处理不足以让用户验证后继续任务。
- 桥接使用 HTTP 会话执行课程请求，错误里只有验证码要求，尚未拿到可供嵌入的验证码页面地址或挑战标识。不能假设 Cookie 复制后即可在另一个浏览器里解除同一挑战。
- 本地 WebUI 的 CSP 当前只允许本站资源；第三方站点也可能禁止 iframe。直接返回上游 HTML 或反向代理整站不是已经验证可行的方案。

以上是代码层面可确认的事实；实际挑战类型、官方验证入口、验证结果与 HTTP 会话的关联方式，需要真实触发样本确认。

## 2. 用户看到的流程

1. 学习遇到验证码后暂停，保留当前课程、项目及站点已确认进度。状态显示“等待人工验证”，页面保持稳定。
2. 课程页出现提示：“智慧树要求验证码验证。完成后可继续当前任务。”主按钮为“开始验证”，同时提供“取消任务”。
3. 当前页展开验证区域，呈现真正运行在智慧树官方来源下的浏览器页面，用户亲自点击、拖动或输入。
4. 用户点击“验证完成，继续”。后端核实官方结果并同步同一会话，确认通过后恢复学习；未通过则保留验证区域并给出原因。
5. 验证过期时显示“验证已过期，请重新开始”，取消时正常结束任务。页面不把等待验证码显示成“任务不可用”或“学习完成”。

若官方验证只能在独立的可见浏览器中完成，当前页保留状态和继续按钮，同时明确提示去该窗口验证；不能把静态截图当作可交互验证码。

## 3. 先完成可行性核对

实施第一步先用人工触发的样本回答以下问题，不以制造大量失败请求的方式触发风控：

- `-12` 出现在什么课程模式、什么操作，官方课程页如何进入对应挑战？是否另有结构化挑战字段？
- 挑战是否绑定 Cookie、请求头、浏览器存储、设备状态或原 HTTP 会话？验证后哪些会话数据实际变化？
- 在受控浏览器完成验证后，原 HTTP 会话能否成功执行一个允许的只读检查？
- 上游是否允许浏览器视图转播？普通可见浏览器是否可用？是否需要完整保留原浏览器上下文？

只记录脱敏的错误码、操作名、课程模式和时间。原始 Cookie、验证票据和完整请求体不进入日志或前端。

核对门槛：必须证明“人工验证 → 原任务恢复”确实贯通，才能承诺原进程继续。若只能恢复登录，采用“保存检查点 → 验证 → 新运行按站点进度继续”，并在 UI 明确表现为恢复运行。

## 4. 任务与桥接改造

### 4.1 在错误被吞掉前识别

在提供者请求边界识别 `CaptchaException` / `-12`，覆盖共享课、校内课及 AI 路径中的宽泛异常捕获。优先在原调用尚未退栈时等待验证，避免上游循环先捕获、返回或把该项目计为完成。

- 发出 `verification_required` 事件，包含 `run_id`、不透明 `challenge_id`、课程模式、当前项目标识和有效期。
- Cookie、挑战票据、请求细节及官方页面地址由后端会话管理器保管，公开事件只带允许字段。
- 验证期间停止新的学习、进度上报和考试请求，保留最后确认的检查点。
- `progress.py` 对等待验证不计成功、不立即计项目失败；`bridge.py` 和终态裁定不能将上游提前返回误判为完成。

### 4.2 明确等待状态与控制通道

在 `CourseStatus` 增加 `waiting_verification`，允许：

```text
running → waiting_verification → running
waiting_verification → stopping → cancelled
waiting_verification → failed（超时、会话失效或不可恢复）
```

同步更新 `domain.py`、`store.py`、`dto.py`、`protocol.py`、`runtime.py` 和前端状态文案。旧任务兼容缺失的验证信息；已有只读摘要契约若需扩展，显式修订对应文档和检查。

现有子进程 stdin 只承载启动参数，需要扩展为持续控制通道，支持验证完成、会话更新和取消。所有命令必须绑定 `task_id + run_id + challenge_id`，旧挑战回复不能恢复新运行。

等待时保留原任务占用的运行槽，并防止同一账号并发执行另一个受影响任务。人工等待默认 10 分钟有效，独立于学习时间预算；现有 `proc.wait(timeout=时限+缓冲)` 需要改成能识别等待状态的期限管理，避免等待期间被旧超时逻辑终止。

取消、超时和服务关闭都必须唤醒等待线程、终止或收尾子进程、释放槽位并关闭验证浏览器。服务重启后不将已失效的挑战自动恢复为运行中。

## 5. 当前页如何承载验证

建议使用“后端受控浏览器 + 本站交互视图”：

1. 在本机创建本次验证专用的浏览器上下文，只进入已核实的官方课程或验证入口。
2. 按真实挑战需求接入原运行会话；Cookie 需保留域、路径、Secure、HttpOnly 等属性，不能只复制成一段前端脚本。
3. 后端将浏览器画面通过本地同源通道展示到课程页，转发用户实际鼠标、触摸和键盘操作。处理坐标缩放、滚动、页面跳转与断线重连。
4. 第三方脚本始终在官方来源的浏览器中运行，不注入本地 WebUI，也不移除上游安全头。WebUI 继续使用本站脚本和资源策略。
5. 若受控视图不被官方挑战支持，切换到用户可见的官方浏览器窗口，并保持当前页的等待状态和继续入口。

这条路径是否支持当前智慧树挑战，以第 3 节核对结果为准；图片转播不能保证替代官方浏览器环境。

## 6. 后端接口草案

以下接口为新增设计，尚未实现：

| 接口 | 用途 |
| --- | --- |
| `GET /api/tasks/{id}/verification` | 返回等待状态、挑战 ID、有效期、可用验证方式；不返回凭据 |
| `POST /api/tasks/{id}/verification/open` | 幂等创建或复用本次验证视图 |
| 本地同源验证视图通道 | 传输画面及用户输入，绑定本次任务与挑战 |
| `POST /api/tasks/{id}/verification/resume` | 以三项标识匹配挑战，再核实官方结果并恢复 |
| `POST /api/tasks/{id}/verification/cancel` | 幂等取消等待和任务，或复用统一停止接口 |

沿用本机 Host、Origin 校验。视图如果使用 WebSocket，握手也要显式校验 Origin，不能仅依赖现有 POST 中间件。验证视图使用短期授权，禁止任意 URL 导航和任意本机端口访问。

恢复之前通过官方验证结果或允许的只读请求确认状态，不以用户按钮或“页面已关闭”作为验证成功依据。会话更新在后端与工作进程之间传递；如需落盘，使用既有凭据保护机制，公开任务 JSON 不保存密钥。

## 7. 恢复与重复提交边界

- 验证完成后更新原工作会话，保留课程上下文，并从最后确认的项目继续。
- 若被拦截的是进度写入、答题或考试提交，先查询站点已有结果，避免盲目重试导致重复提交。
- 若原进程无法继续，创建新运行并读取站点真实进度；不要按前端百分比推断已完成内容。
- 恢复后再次遇到验证码，创建新的挑战并保持等待，不自动循环提交或反复发起验证。
- 验证状态变化做增量更新，保留当前目录展开、滚动与参数编辑状态，沿用本次修复后的防重复重绘逻辑。

## 8. 实施顺序与验收

1. **明确识别与提示**：先完成挑战识别、独立错误类别与当前页提示，确保验证码不能伪装成普通失败或正常完成。
2. **暂停与人工验证贯通**：实现等待状态、控制通道、官方浏览器验证、后端核实和恢复；先打通一个真实课程模式。
3. **当前页交互视图**：接入浏览器画面和用户操作，补可见浏览器回退，并验证另外两种课程模式。
4. **生命周期与回归**：检查超时、取消、服务退出、断线和会话过期，再交付完整功能。

验收至少覆盖：

- 真实 `-12` 样本和上游内部捕获路径，不只测试手工构造的错误文本。
- 验证通过、未通过、过期、重复点击和旧 `run_id` / `challenge_id` 回复。
- 等待期间不新增学习请求，不增长完成计数，不被原学习时限误杀。
- 关闭页面、停止任务和关闭服务能够清理所有等待进程及浏览器。
- 验证后恢复官方已确认进度，不重复答题、提交或重新创建课程任务。
- 日志、任务文件、API 响应和前端存储中无 Cookie、票据或模型密钥。
- 连续轮询不重建验证视图，不打断用户拖动和输入。
