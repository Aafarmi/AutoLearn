# P21 · 开局判定一次 / 视觉组只翻译 / 置信度两口径 / 回读三态

**日期**：2026-09-30 · **触发**：用户四条实测判词（每条都是需求，不只是 bug 报告）

---

## 一、用户原话

1. 「下一题处理仍然存在严重问题，现在严格按照我的方法修改，程序开始运行时需要有一套判断逻辑，
   一旦判定好后后续的全部按照这套逻辑」
2. 「两套模型配合出现严重问题，视觉组模型的任务就是解读照片，将照片翻译成固定格式，
   解题组模型严禁拿到非文本输入」
3. 「置信度系统也存在bug，如果不使用复算系统则不存在置信度系统。目前不开启复算时存在
   模型无法解题的情况，处理这个bug」
4. 「动作 回读不一致判断逻辑存在问题，存在点击正确却判断错误导致胡乱操作」

四条背后是**同一条纪律**：**判断只做一次，之后按它执行；做不了就如实停下。**
旧版每一处都在「临场再判断一次」—— 而那正是跳题、误点、误停的来源。

## 二、① 开局判定一次（`core/run_plan.py`）

新增 `derive_plan(batch, *, batch_size=0) -> RunPlan`，把**四件事**在开局读图那一次定死：

| 定死的东西 | 取值 | 依据 |
|---|---|---|
| 推进方式（**恰好一种**） | `CARD` / `CLICK` / `SCROLL` / `SWIPE` | `core/advance_library.PLAN_PREFERENCE = (CARD, CLICK, SCROLL, SWIPE)` |
| 推进几何 | `control_box`，或答题卡 `card_origin`/`card_step`/`card_anchor` | 答题卡按行换行 `divmod(index, cols)`，容差 `CARD_GRID_TOLERANCE=0.10` |
| 提交范围 | `PAPER` / `QUESTION` | 观测说了算；没有则「有答题卡 / 总数≥2 / 一屏≥2 题」→ 整卷 |
| 总题数 | 整数或「不知道」 | 不知道时 `reached_total()` **永远 False** |

**删掉的东西**（每一条都对应一次真机事故）：

- **换招阶梯**（点击 → 滚动 → 滑动）：P20 那种「滚了 4.8 屏、题号从第 3 题跳到第 16 题」就是它；
- **每题重问「下一题在哪」**（`find_advance_control`）：同一个按钮两次给的框差了 0.8 个屏宽；
- **「滚到顶重读一次」**（`_reread_at_top`）：把刚滚到的位置毁掉，读回来的是更早的题；
- **「这一屏没有提交按钮就中途暂停」**：`logs/10ca5ee8c89e` 44 题做到第 16 题停在这儿 ——
  整卷页面上「中间几屏没有交卷按钮」本来就是正常形态。

推不动 → `_settle_end`：请视觉组确认「是不是全部完成了」→ 确认才干净收工，
否则 `advance_failed` 停下等人（**绝不静默跳过**）。

### P20 留下的那道题（5 题同页、只有题号导航）现在有解了

旧版 `method` 说得出 `click` 却**给不出落点**，于是只能做第 1 题。现在这种情况裁决成 `CARD`：
点答题卡上「下一题号」那一格，落点由网格算术给出。三条配套纪律：

1. **锚点优先用模型直接指出的下一题号格**（`card.next_box`）—— 它是对「下一次该点哪里」的正面陈述。
   用它的额外好处：**题号观测可以缺失**（`current=None`）而落点照样准；
2. 落点算不出来（超出卡片可见区域 / 缺列行数）→ **不点**，整条 CARD 回退；
3. 推进后读到的题号与预期不符 → `advance_failed` 停下（防静默跳题）。
   题号来源不可信时（`current` 没观测到）**不做这个校验** —— 拿猜出来的题号比对会把正常推进判成跳题。

## 三、② 视觉组只翻译、解题组只看文本

- 视觉组（`prompts/00-共享契约.md` + `10-视觉组.md` → `solve/reader.READ_SYSTEM_PROMPT`）
  所有请求回**同一份固定格式**：`{"page": {...}, "questions": [...], "more_below", "note"}`。
  `page` 只报告「有什么」（进度 / 总数 / 当前题号 / 推进控件 / 答题卡 / 提交框与范围 /
  是否做完 / 能否滚动），**不报告「该怎么办」** —— 裁决在程序侧。
- 解题组请求里 `images` **恒为空**，而且在 `solve/solver.py::Solver._complete` 里加了一道
  **硬闸**：请求带图 → 当场 `RuntimeError("解题请求不许带图…")`。
  为什么用硬闸而不是「记得别加」：真机上发图之后推理模型会**不回答、只烧 token**
  （`content` 留空），这种故障从输出上完全看不出来。**取消选项打乱**（p6.0）：
  标号就是页面标号（可能不连续 `A、B、D`），`voting.resolve` 按**页面标号定位**、按内容归并。
  打乱是「标号串位」那条历史事故的成因，取消之后这一类错误从根上没有了。
- 提示词 **3 份 → 5 份**：删 `30-起始标定.md` / `31-收尾确认.md` / `32-推进控件.md`；
  `solve/reader.py` 只剩 `READ_SYSTEM_PROMPT` + `parse_page_view` / `parse_read_batch` /
  `parse_read_payload` / `gate_read_result` / `read_question` / `read_questions`。

## 四、③ 置信度：不开复算时用模型自报值

- 解题组输出新增**必填** `confidence`（`parse_confidence` 认 `0.8` / `"0.8"` / `"80%"`，
  越界**夹到** `[0,1]`，bool/NaN → `None`）。
- 不开复算（`sample_n == 1`）→ 用自报值；低于 `guards.confidence_review_min`（默认 0.5）
  → `⚠复核` **必停**。开复算（`n > 1`）→ 多数票占比，自报值不参与。
- **不可用的单次回复**（无 content / 解析不出 / 标号越界 / provider 报错）改判为**请求失败**
  → 有界重发 `SAMPLE_RETRY_MAX = 2`（每条采样项最多 3 次请求），**不是**复算；
  **显式空作答是模型的结论**，不重发。

**为什么原来会「模型无法解题」**：不开复算时只有一次采样，那个 1.0 的一致率不含任何信息；
一次网络抖动或一次输出截断就会让 `chosen_labels=[]`，于是题被记成 `empty_answer` ——
用户看到的是「模型解不了这道题」，真因只是那一次回复坏了。开复算时第二个样本能顺手救回来，
所以这个故障**只在不复算时暴露**。

## 五、④ 动作回读三态

`act/verifier.py`：`region_change_state(mad)` → `changed`（`≥REGION_CHANGE_MIN_MAD=2.0`）/
`weak`（`≥REGION_CHANGE_WEAK_MAD=0.05`）/ `none`；`verify_region_changed` 的
`ok = state in {"changed","weak"}`，`actual` 形如 `region_mad=0.31 state=weak`。

`act/actuator.py::select_option` 按**落点**分档：

| 落点 | 回读 | 处置 |
|---|---|---|
| `ink_centroid`（选项自己的文字上） | `changed` / `weak` | 成功收工 |
| `ink_centroid` | `none` | **绝不重点**（`ok=True`，readback `no_change_on_ink:…`） |
| 几何兜底 | `changed` / `weak` | 成功收工（换点前先重测） |
| 几何兜底 | `none` | 换下一个候选点 |
| 全部候选 | `none` | `_exhausted`（`ok=False` + 截图 + pause） |

**为什么**：画面本来就没什么可变时（选中态很轻、纯图片选项），旧判据判「没点中」→
反复换点、乱点一气；多选题上那一下会把刚选上的勾**取消**。重复点正是用户报的「胡乱操作」本身。

## 六、顺手补掉的四个真问题（都由测试驱动发现）

1. **「只有 page 观测、没有题目」的开局屏拿不到方案**：`_last_batch` / `_last_size` /
   `_last_submit` 原先记在「至少一道题过门禁」之后，于是那种开局屏会把整份观测丢掉 →
   整条运行在 `no_plan` 上打转。现在观测在**解析成功**时就留下（`page` 是页面级事实，
   与这一屏有没有读到题无关）。
2. **关掉开局判定（`guards.advance_calibrate=False`）+ 每题提交 ⇒ 必然 `vision_no_submit_box`**：
   提交框只有「开局方案」与「收尾那一屏」两个来源，而每题提交要的正是「当前这道题所在那一屏」的按钮。
   现在多了第三个来源 `_last_submit`（最近一次读图看到的框），并按范围排序：
   `PAPER → [方案, 收尾, 最近]`，`QUESTION → [方案, 最近, 收尾]`。
   **每一对框与尺寸永远同源**（拿 A 屏的框配 B 屏的尺寸就是历史上那次「点歪了」）。
3. **开局那一次读图把首屏第 1 题**（`accepted[0]`）**丢掉了**：`_read_question_by_vision`
   只把同屏**其余**题入队、把第一道**返回**给调用方，而 `_plan_run` 没人接这个返回值；
   主循环又**先取队列**，于是「一屏多题」时首屏第 1 题**静默跳过**，而单题屏则被**读第二遍**
   （白花一次调用）。现在 `_plan_run` 把它 `insert(0, ...)` 放回队首 ——
   与滚动那条路（`_scroll_reveal_next` 早就有这一句）的约定一致。
4. **整卷提交后其余题停在 `applied`**（不是终态）：整卷只有一次提交动作，回读只挂在
   「最后作答的那道题」上。续跑时 `applied` 会被**重做一遍** —— 多选题上重新点选项
   就是把刚选上的勾**取消**。现在提交确认后 `_settle_paper_batch()` 把这一轮其余
   `applied` 的题按 `applied → submitted → verified`（状态机里 `applied` 没有直达
   `verified` 的边）一并推到终态；**提交失败/暂停时不推**（那一卷结果未知，保持原状才诚实）。
