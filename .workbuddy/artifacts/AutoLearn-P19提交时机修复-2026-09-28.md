# P19 · 整卷页面「做一题交一次」的提交时机修复

**日期**：2026-09-28 · **触发**：用户实测报告（作业页 44 题，第 1 题作答后立即走到「已提交」）

---

## 一、现象

```
21:21:23 log.line {.., "batch":2, "queued":1, "has_submit_box":true}
21:21:43 条目状态：已应用 → 已提交
21:21:44 条目状态：已提交 → 失败
21:21:44 run.paused (submit_timeout)
```

用户的话：**「题目没有全部完成就提交了」**。

---

## 二、根因（证据齐全，不是推测）

留痕目录 `logs/de615cf6d625/de615cf6d625-v957967f3e7a3989/`：

| 证据 | 内容 | 说明 |
|---|---|---|
| `action.json` | `{"kind":"submit","ok":true,"elapsed_ms":70}` | 点击**确实发出去了** |
| `verify.json` | `region_mad=0.06`（阈值 ≥2） | **画面纹丝不动** |
| `before.png` | 左侧答题卡 `0/44题`；题 1/2/3 纵向排列；右上角**唯一**一个「交卷」 | 这是**在线作业页**，每题**没有**独立提交按钮 |

离线量过落点（用那张 `before.png` 跑落点算法）：`ink_centroid` 稳定落在 **(877.5, 66.3)** ——
正在交卷按钮里。**落点是对的**。

> **真根因**：这是「整卷交卷」型页面，程序却按「每题提交」在做 —— 第 1 题做完就去点了「交卷」。
> 那个按钮在 `0/44题` 时**被禁用**，所以点了毫无反应、以 `submit_timeout` 停下。
>
> 这次只是停下。**站点若允许交卷，那一按就是用户剩余 43 道题的作业当场作废。**

`prompts/10-视觉组.md` 里原本写着「`submit_box` = 提交按钮」，但从没说过它**管多大范围** ——
程序就只能假设「每题一个」。这个假设只对靶场成立。

---

## 三、修法（三层）

### 1. 视觉组输出新增 `submit_scope`（提示词）

`prompts/10-视觉组.md` 新增专节「提交按钮的范围」：

| 取值 | 判据 | 典型文案 |
|---|---|---|
| `question` | 紧挨某道题、只管这一题 | 「提交」「提交本题」「确定」 |
| `paper` | 页眉/页脚唯一一个、管整份 | 「交卷」「提交试卷」「提交作业」 |
| `null` | 画面上没有提交按钮 | —— |

提示词里把**后果**写进去了（这是唯一能让模型权衡判错的代价的地方）：

> 把 `paper` 报成 `question` ⇒ 程序**每做完一题就点一次这个按钮** ⇒
> 在整份作业上就是**做完第 1 题交卷**，用户剩下 43 题全部作废且**不可撤销**。
> 所以**拿不准时往「整卷」那边靠**。

配套：`core/enums.py::SubmitScope`、`core/models.py::ReadResult.submit_scope`、
`solve/reader.py::_submit_scope_of`（**只认明确词** —— `"submit"` 这类含糊说法一律 `None`，
**猜错的方向是提前交卷**）、`prompts/00-共享契约.md` 同步。

### 2. 编排层按范围决定时机

`core/orchestrator.py`：

```
question 模式 → 每题 _apply 后就 _submit_and_confirm        （既有行为，靶场不动）
paper   模式 → 每题只 _apply；提交推迟到主循环结束后的收尾
               └─ _submit_paper_once()：四道前提，缺一不做
                    ① 视觉组确认过「全部完成」（_completion_confirmed —— 主闸门）
                    ② 这一轮真的点过选项（_last_applied_item_id）
                    ③ 范围是整卷
                    ④ 还没交过（_paper_submitted —— 提交绝不重放）
```

判定三层（`_submit_scope_of_run()`）：
**模型说的最可信** → 模型没说就看**结构性证据**（本次运行一屏读到过 ≥2 道题 = 连续卷面）→
都不成立才退回 `question`（**保住靶场的既有行为**）。

### 3. 断点续跑路径同步

`_step_quiz` 里「已选未提交 → 补提交」那条断点路径，在 `paper` 模式下**不再补提交**
（选项早已落在页面上，补一次就是提前交卷）。

## 四、顺带抓到并修掉的两个真 bug

两个都不是靠读代码发现的，是**测试逼出来的**：

### A. `_find_item` 拿 `qid` 查 `item_id` → 整卷提交**永远不发生**

我最初把 `_last_applied_qid` 存成 `item.qid`，而 `_find_item` 按 **`item_id`** 索引 →
**静默返回 `None`** → 提交被跳过。**不报错、不留痕**，唯一现象是「什么都没提交」。

> 是诊断脚本（打印 `_completion_confirmed` / `_last_applied_*` / `_submit_scope`）把它定死的。
> 已改为存 `item_id`，并在注释里写明「存错只会静默查不到」。

### B. 「一屏多题省调用」**从未真正生效**

`_drain_quiz` 每轮末尾都走 `_advance`，而 `_advance` **入口清空 `_pending_reads`** ——
于是同屏读到的第 2、3 题，下一轮必然被丢掉。日志里 `batch:2 queued:1` 看着很省，
实际下一题又从头读了一次图。

> 这是 P17 引入队列时就存在的缺陷（几何是**相对视口**的，一滚就作废，
> 所以「复用同屏几何」与「做完一题就推进」不能共存）。
> 修法：`_pending_reads` 非空时 `continue` —— **先把这一屏做完，再推进**。

## 五、界面修复

| 现象 | 原因 | 修法 |
|---|---|---|
| 日志里「动作降级到 **?**」 | 事件负载字段是 `level`，前端读的却是 `level_used` | 改正字段名 + 补 `LEVEL_LABELS`（「动作执行层级：模型坐标」） |
| 跑一次出现两次「发现新任务」 | `task.created` 被两种语义共用（建任务 / 认领条目） | 前端按负载里的 `item_id` 区分（「认领一道新题（新建条目）」） |

另：视觉读题的原始产出（含**每个 box** 与 `submit_scope`）现在落盘为 `vision_read.json` ——
这次的排查最缺的就是「模型给的框到底在哪」（`perception.json` 刻意不含几何）。

新增测试钉住的是**顺序**（这是唯一能把「提前交卷」和「正确交卷」区分开的判据）：

```
paper    : [select_option, select_option, submit]          ← 两题做完才交一次
question : [select_option, submit, select_option, submit]   ← 每题交（靶场行为不变）
paper + 未确认完成 : [select_option, select_option]          ← 一次都不交
```

## 七、后续建议

1. **`submit_scope` 依赖模型自述** —— 结构性兜底（一屏多题）能覆盖大部分真实作业页，
   但「一屏一题的长卷」仍要看模型脸色。若以后遇到误判，可考虑让视觉组**同时给出按钮文案**
   （`submit_label`）作为交叉验证。
2. **整卷提交目前是全自动的** —— 若希望「交卷前再问人一次」，可在 `_submit_paper_once` 里
   接 `_await_human`（半自动模式下已经逐题确认过，所以现在默认直接交）。
3. **`.bat` 与 `run.bat` 的提示文案**已说明可用界面「关机」收尾，无需手动关两个窗口。
