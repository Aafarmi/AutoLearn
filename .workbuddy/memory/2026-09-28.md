## 1. 需求 1：核对次数 5 → 1（有一个容易漏的点）

`MIN_SAMPLE_N` 5 → 1，`RunConfig.sample_n` 默认 1 —— 这两处是显然的。

**容易漏的是第三处**：`GuardThresholds.tier2_min_votes` 原本是 **3**，而它是
`Solver._build_batch` 的地板（`max(sample_n, minimum)`）。
带图 / Canvas 题**直接走 Tier2**（`direct_tier2 = has_image or _needs_vision(...)`），
所以只降 `sample_n` 的话，那类题仍然会采 3 次 —— 用户看到的还是「明明改了却还在多次核对」。

**机制保留**：投票、一致性复核、升 Tier 都还在，只是默认不再多重采样。
把 `sample_n` 或 `tier2_min_votes` 调高即可恢复。

## 2. 需求 2：一套配置一个模型 + 四组选择

### 2.1 模型库

`ModelProfile.tier1_model` + `tier2_model` → **`model: str`**。
`CapabilityReport.tier1_ok` + `tier2_ok` → **`model_ok`**（单模型下两个勾必然一样，
留着只会让人以为有两套模型）。Tier 语义仍在（Tier2 = 升级复算），
但 `model_for(tier)` 现在任何档位都返回同一个模型名。

**旧数据迁移**（`migrate_profile_payload`，`ModelRegistry.load()` 自动调用）：
取 `tier1_model` 作为 `model`、丢掉 `tier2_model`。

⚠️ **第一版迁移漏了 `capabilities`**，用用户真实的 `state/models.yaml` 一试就炸：
`ValidationError: capabilities.model_ok Field required / tier1_ok Extra inputs are not permitted`
—— 因为那份报告也会落盘，而 `ModelProfile` 是 `extra="forbid"`，
**顶层字段迁对了、嵌套没迁，整份文件照样加载失败**。
补上「`tier1_ok or tier2_ok` → `model_ok`」后，用户那三套配置（`com-dsv4.1` / `deepseek` /
`glm-4.6v-flash`）全部正确迁移，且实测报告里的视觉结论保留下来（不用重测）。

### 2.2 任务四组

用户先说的是三个组，追问后明确**备用组也要分视觉 / 解题两份**，所以是四组：

| 界面 | 字段 | 数量 |
|---|---|---|
| 视觉组 | `vision_profile_id` | 1 |
| 视觉备用 | `vision_backup_profile_ids`（新增） | **多选** |
| 解题组 | `model_profile_id` | 1 |
| 解题备用 | `backup_profile_ids`（新增） | **多选** |

链路 = `主选 → 备用（按用户勾选顺序）`。三个边角必须想清楚，否则会出现
「我明明选了 A，它却用了 B」或者反过来「配了备用却永远用不上」：

1. 主选与备用**都为空** → 退回整条活动链（保持 P4~P13 的降级链语义）；
2. 备用里的**死 id**（配置已被删除）→ 忽略，而不是「所以干脆用整条活动链」；
3. 视觉链**只在用户真选过视觉组**时单独构造 → 否则留空，由 `_vision_providers()`
   回落解题链（「视觉组留空 = 与解题组共用」靠这条成立）。

字段名 `model_profile_id` 故意不改名（改了会让已存盘的 `state/run_config.json` 失效），
只改界面标签「判题模型」→「解题组」。

## 3. 需求 3：抓取网页 + 反馈

按钮文案按目标类型分派：网页「抓取网页」、程序「抓取窗口」、进行中「抓取中…」。

**原来的真问题不是文案，而是没有任何反馈**：抓取成功时只有下拉框悄悄变了一下，

## 4. 需求 4：末题判定整套推倒

用户判定 P14 那套「靠进度正则与终点文案拼证据、猜不出来就问用户」**逻辑有严重错误**，
要求全推。删掉的东西：`perception/end_probe.py` 整个模块、`run_flag` 表与三个函数、
`POST /api/tasks/{id}/last-question`、`LAST_QUESTION_UNCERTAIN` 错误码与引导卡、
前端确认块、两个旧事件、`tests/test_end_of_quiz.py`、8 个 `end_*` / `advance_scroll_*` 旋钮。

新流程（`AdvanceMethod` + `TaskCalibration` + `CompletionCheck`）：

```
任务开始 ──► 视觉组标定：total（总数）+ method（点击 / 滑动 / 滚动 / 看不出来）
             逐题解题（按 method 分派推进顺序）
   已完成数 == total  或  所有推进方式都用尽
             └──► 视觉组再确认「是否全部完成」
                      ├─ true  → finished
                      └─ 否则  → advance_failed 停下
```

四条纪律（每条对应一种真实错法）：

1. **`total` 不是正整数就按「不知道」**；不知道总数时 `reached_total()` **永远 False**
   —— 「不知道」绝不等于「做完了」（这是唯一会导致跳题的推理方向）。
2. **问不成 = 未确认**：没有 provider / 截图失败 / 解析失败 / 答非契约 → 一律 False → 停下。
3. **同一题同一触发点只问一次**（`_completion_checks`，键 `(qid, trigger)`），
   否则会在「推不动 → 问 → 说没完成 → 再推 → 再问」之间绕圈。
4. **标定失败不终止任务** —— 没配视觉模型的人也必须能跑（退回默认阶梯）。

**语义边界不变**：视觉 / 滑动兜底仍只在无锚点站点启用；有锚点站点
「没有下一题按钮 = 干净跑完」不许动，否则靶场跑批的收尾会从「跑完」变成「暂停」。

## 5. 事故：我删掉了 `core/config.py`，以及怎么救回来的

**经过**：改配置层时，我把一条 `Remove-Item -Path core\config.py` 误写进了校验命令里
（本意是删临时脚本），**文件被删除**。`Remove-Item` 不进回收站，仓库也没有 git。

**抢救**：唯一的线索是 `core/__pycache__/config.cpython-313.pyc`（用户 11:10 启动程序时编译的）。
`.pyc` 可以被 Python **直接加载成模块**，所以没有去反编译，而是：

```python
loader = importlib.machinery.SourcelessFileLoader("_cfg_old", pyc)
loader.exec_module(mod)          # 先把模块注册进 sys.modules，否则 pydantic 解析不了前向引用
mod.RunConfig.model_fields       # → 字段名 / 注解 / 默认值 / default_factory 全部权威可读
```

据此逐字重建，并写了一个**逐字段比对**脚本（旧 pyc vs 新文件）：

| 比对项 | 结果 |
|---|---|
| `GuardThresholds` / `RateLimits` / `RunConfig` 共 35 个共有字段 | ✅ 名称、**顺序**、注解、默认值、`default_factory` 全一致 |
| 模块常量（`MIN_SAMPLE_N` / `PROBE_CHAINS` / 路径 / 环境变量名） | ✅ 一致 |
| `__all__` / 函数签名 / `RunConfig()` 默认 dump | ✅ 一致 |
| 全部差异 | 仅「有意删掉的 8 个 P14 旋钮 + 有意新增的 2 个标定旋钮 + 2 个备用组字段」 |

**第一轮比对还漏了一处**：只比了 `model_fields` 与函数，**没比 property**。
后来 `mypy` 报 `"RunConfig" has no attribute "llm_concurrency"` 才暴露 ——
补回 `is_model_ready` 与 `llm_concurrency`（用反汇编 + 行为探测确认语义：
选了模型走 paid 并发档、没选走 free 档）。**教训：类比对要含 property / classmethod。**

**残留差异（必须如实说）**：注释不在字节码里，无法恢复。`GuardThresholds` 前半段注释
我此前逐字读过、按原文复原；**`RunConfig` 各字段的注释是按语义重写的**。
功能零损失，措辞非逐字。

**由此定下的规矩**：删除操作 ① 只删**显式列出的单个文件**；② 每个路径先校验在仓库根之下；
③ **绝不把删除命令与其它命令写在同一条命令里**。

### 14.2 三条设计决策

1. **只关自己起的**：归属三态 `self` / `sibling` / `foreign`，三条同时满足才动手
   （端口在名单 + 不是自己 PID + exe 与本进程解释器一致），否则**只报告**。
2. **先回执、后动手**：收尾挂 `BackgroundTasks`，`apply_shutdown` 自带 0.35s 宽限
   + 4s 兜底硬退。抢在响应之前杀进程 = 用户看到一次莫名其妙的连接重置。
3. **成败由探活判定**：响应常被进程退出截断（fetch 直接 reject）→ 前端用 `/api/health`
   探活，避免把「其实关成功了」报成失败。

### 14.3 施工中抓到的真 bug（只有真起服务才暴露）

**虚拟环境下 `sys.executable` ≠ 进程镜像路径。** 冒烟实测：靶场进程被判成 `foreign`
（`QueryFullProcessImageNameW` 报的是 `.venv` 背后的**基础解释器**），于是清单写
「端口 8899/8900 被别的程序占着，不会动它」，**一个都没释放** —— 功能看着在、其实没生效。
修法：`own_executables()` 返回 `sys.executable` + `sys._base_executable` 作为**一组**候选。

> 教训：这类坑**纯单测永远发现不了**（单测里 exe 查询是我注入的假函数）。
> 归属判定必须靠**真起两个进程**来验 —— 这正是「端到端冒烟」不可省的理由。

另：前端把占位 `li` 与真清单混在一个元素里，自检在「请求还没回来」的瞬间把占位读成清单
（清单只 1 条且不含端口）；拆成两个元素后解决。

## 18. P20：推进不按标定 + 滚动盲目连滚 + 批量删除 + 重试

### 18.1 用户报的两件事（附铁证）

### 18.3 新功能

- **批量删除**：`POST /api/tasks/bulk-delete`（`{"run_ids": [...]}` → `{"deleted": [...], "skipped": [{run_id, reason}]}`）
  —— **逐条回报**：正在跑的那条跳过并说明原因、其余照删。前端任务卡加多选框 + 工具条「全选 / 删除选中 (N)」。
- **重试**：`POST /api/tasks/{run_id}/retry` —— 与 `start` **共用 `_launch`**（断点续跑天然成立：
  `_restore` 按 qid 认领、`_drain_quiz` 跳过 `is_terminal` 的题）。任务卡上对「没跑完、没在跑」的任务显示「↻ 重试」。
