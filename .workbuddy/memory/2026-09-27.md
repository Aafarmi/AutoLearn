## P11 修订（同日 · 用户反馈后）：接管启动两个真 bug + 桌面应用程序采集

用户反馈：①「接管启动」没把前置做全，标签页识别不出来；②还要抓正在运行的**应用程序**并用视觉识别。

### 查出的两个确定性缺陷（都是实测复现，不是猜测）
1. **Chrome 136+ 会「静默忽略」为默认 Profile 目录开的调试端口**
   - 官方公告原文：从 Chrome 136 起，为**默认**数据目录开 `--remote-debugging-port` **不再被遵循**，必须搭配指向**非标准目录**的 `--user-data-dir`
   - 旧实现传的正是 `%LOCALAPPDATA%\Google\Chrome\User Data`；本机 **Chrome 153** → 接管启动从来没成功过（进程起、窗口开、端口不开 → 扫描永远 0 标签页）
   - 旧报错把它归因成「已有实例在运行」→ **归因错误**，排查方向完全跑偏
   - 修复：改用**自管非标准目录** `state/browser_profile/<channel>/`（顺带解决「与用户浏览器抢 profile」→ 用户不必先关浏览器）
   - 代价：全新浏览器身份，首次需登录一次（官方推荐做法，唯一能同时满足「端口可用」+「不动用户数据」）
   - `default_user_data_dir()` 已改名 `system_user_data_dir()`（语义：只用于展示/排障，**不得用于启动**）
2. **Chrome 不接受相对路径的 `--user-data-dir`** → 退出码 **21**，且 **stderr 一个字节都不吐**，profile 目录一个文件都不建
   - 同一位置：相对路径 → 21；绝对路径 → 端口正常（对比实验定位）
   - 隐蔽点：`check_target.py` 当时**是绿的**（它用 `tempfile` 绝对路径）→ 典型「测试绿、产品挂」
   - 修复：构造时 `.resolve()`；报错文案写明「21 = 相对路径/无写权限」+ 打印实际数据目录；留回归用例
3. 顺带：新 Profile 起始只有空白标签页 → 接管启动时把 `ui/static/landing.html` 作位置参数交给浏览器

## 修复「测试连接」的视觉假阴性（用户实测反馈，**用户判断正确**）

用户：DeepSeek 4.1 支持图像理解，但「测试连接」报不支持 → **用户是对的，我的测试方式有毛病**。

### 对照实验（同模型同参数，只改探针图）
| 探针 | 结果 |
|---|---|
| 1×1 透明 PNG（原实现） | **400** `"You have uploaded an unsupported image..."` → 误判不支持 |
| 换成真实图 | 200，模型答出图中数字 |
| 换回 1×1 | 400 又失败 |

`deepseek-flash` 与 `deepseek-reasoner` **两个 tier 都能正确读出图里的数字**。

### 三处缺陷（都已修）
1. **探针图是 1×1 透明 PNG** → 厂商判为非法图像回 400 → 假阴性。
   修：`_probe_image()` 用 PIL 代码生成 256×256「白底大黑数字 7」（缺省位图字体 16×16 再 NEAREST ×16）。
   选数字不选颜色：**语言无关**（问颜色会得到「红色」/「red」两种答案）。
   **不引入二进制资源**，可复现可审阅。
2. **探的模型不是用的模型**：`solver` 见图直接升 Tier2，`complete` 用 `model_for(tier)` → 图片实际发往
   **tier2_model**；而探针吃 `_chat_body` 的 tier1 默认值。
   修：新增 `_vision_body()`，显式传 `tier2_model or tier1_model`。
3. **`max_tokens=16` 太小**：`deepseek-reasoner` 在 64 下正文为空（预算被思维链吃光），256 才能答出 `7`。
   修：视觉探针用 256。

- conftest 假端点新增 `vision` 模式（对带图请求回 "7"）用于校验强证据路径

**假阴性比漏测更糟**：它会让人去改本来没问题的配置。凡是「探针判定」，

## P11 增量：视觉「读题」契约（真实站点终于读出来了）

### 缺陷 1（把整条兜底链路堵死）
`VisionProbe.is_available()` 去查 `question_root`（靶场 `data-quiz` 锚点），锚点不在就弃权。

## 接线 bug：读题成功但任务立刻判失败（用户第二次贴日志）

日志：`vision_read=ok qid=... options=4` → `task.created` → `to=failed` → `run.paused reason=perception_failed`。
**每一步都成功、结果却失败**，看上去像「没读到」，其实读到且完全正确。

### 根因（我接线的错）
读题结果只落在 `_drain_quiz` 的**局部变量** `question` 里，而下游
`_step_quiz` 只认 `perception.question`（仍是 `None`）→ 立刻 `FAILED` + `perception_failed`。
修：`perception = perception.model_copy(update={"question": question})` —— **并入感知结果**，
而不是另开一条变量往下传。分成两条路，必然在某处漏掉一条。

### 顺带修的第二个
`has_submit_box=false`：提交按钮在页面顶部，滚到下方时截不到，模型如实回 null。
→ 找不到提交框时**滚到顶重读一次**（有界恢复，只一次；且只接受**同一题干**的重读结果，
换了题就不认）。仍找不到则明确停并给出可操作提示。

### 新增回归用例 `tests/test_vision_read_flow.py`（5 条，全内存，永不 skip）
用**自建最小替身**（假 provider 回合法读题 JSON + 假 page 记录 `mouse.click`）驱动
完整的 `orchestrator.run()`：
1. **核心守卫**：读题成功后任务必须以 `submitted` 收场，且暂停理由**不是** `perception_failed`
2. 坐标换算：点选项 `(330, 225)` + 点提交 `(945, 15)` —— 由 1000×600 的图手算验证
3. 按坐标的动作落在 `l6_vision_xy` 阶梯（热力图靠它区分「DOM 点到的」与「模型看着点到的」）
4. 找不到提交框：只点选项、**绝不点提交**，停在 `applied`
5. 填空题（不支持题型）：**一个坐标都不点**，不建任务，停下说明

### 教训
「每一步都成功、结果却失败」的 bug 最贵。**中间产物必须在正确的层上落定**，
不能靠并行变量传 —— 两条路传同一份数据，迟早漏掉一条。

## P12：「进入下一题」—— 点击 + 滑动两条路（同日，用户实测反馈）

用户反馈：**简单选择题已经能跑，但进入下一题不行**。
「有的题目是点击下一题，有的是滑动下一题；如果图片里没有下一题的选项就要尝试滑动下一题」。

### 根因（一条 `count() == 0` 就把整批截断）
`Orchestrator._advance()` 原来只有一条路：取 `selectors.next` 锚点按钮 →
`count() == 0` 就 `return False` → 主循环把 `False` 当「跑完了」。
真实站点没有靶场那套 `data-quiz` 锚点 → `count()` **恒为 0** → **只做第一题就结束**，
而且看起来完全像「题库就这么大」，极难发现。

### 修法：`_advance` 改成三段阶梯（顺序即降级顺序）
1. **DOM 锚点**（`selectors.next`，走六级阶梯）—— 靶场与配了锚点的站点，零成本
2. **视觉按钮** —— 先用**读题那一次读图**给的 `next_box`（零模型成本）；
   点不动（页面指纹没变）再**现读一张**（专用小 prompt，只找「下一题/继续/下一页」）
3. **滑动** —— 按 `guards.advance_swipe_directions`（默认 `left` → `up`）逐个试
4. 全失败 → `advance_failed` 暂停 + 给出可操作 hint

**语义边界（关键）**：第 2/3 段**只在当前题是视觉读出来的时**才启用
（`guards.advance_visual_fallback` 且 `qid in _vision_reads`）。
有锚点的站点上「找不到按钮 = 没有下一题了」**保持不变** —— 否则靶场跑批到最后一题会乱滑，
最后以假故障 `advance_failed` 收场（那就是把跑完变成报错）。

### 新增件
- `core/enums.py`：`ActionKind.SWIPE`（**不新增 ActLevel**：手势落 `L6_VISION_XY`，
  保住「六级阶梯」这条冻结契约与 `set(MEDIA_LEVELS)==set(LEVELS)` 的既有断言）
- `act/actuator.py`：`swipe(direction, mode=mouse|touch)` + `_swipe_path`/`_interpolate`/`_touch_point`
  - **必须有中间点**（8 步）：`down → move → up` 一步到位会被手势库判成**点击**
  - `touch` 模式要先 `Emulation.setTouchEmulationEnabled`，否则页面在特性检测阶段就关掉触摸分支
  - 视口尺寸**不能只看 `page.viewport_size`**（CDP 附加来的页面常为 None）→ 回退读 `innerWidth`
- `solve/reader.py`：`ADVANCE_SYSTEM_PROMPT` + `parse_advance_payload` + `find_advance_control`
  - **`{"box": null}` 与「没看成」严格区分**：前者是「看过了，画面上没有」（→ 去滑动），
    后者是工具故障（`(None, 错误码)`）。混在一起会让编排层把故障当成页面事实
  - 提示词点名排除「上一题 / 返回 / 收藏 / 提交答卷」—— 认错反向控件就是把做过的题重做一遍
- `core/models.py`：`AdvanceLook`
- `core/config.py`：`guards` 新增 6 个旋钮（兜底开关 / mouse|touch / 方向序列 / 行程 / 时长 / 判定预算）
  UI 表单不含 `guards`（`PUT /api/run/config` 用 `exclude_none=True` 合并）
  → 改法：`state/run_config.json` 或 `AUTOLEARN_GUARDS__ADVANCE_SWIPE_MODE=touch`
- `scripts/check_read.py --locate-next`：只问「画面上有没有下一题」，**不点不滑**，
  三种结论分开报（有 / 没有 / 没看成）

### 「判不了就不许连滑」—— 本条最该记住
`_page_signature()` = `URL + 题目区文本哈希`。**取不到可判定内容**（canvas 题的正文为空）
时返回 `None`，此时**只做一次动作**。因为把「没变」当结论会再滑一下 ——
第一次其实成功了的话就**一次跳过一整道题，而且跳得悄无声息**。跳题是硬禁区。

### 验收
- 纯内存 `tests/test_advance_next.py`（11 条）：三段阶梯每个分支 + 方向回退 + 判不了只滑一次
  + 全失败必停 + **两题连做的端到端**（滑动推进 / 点按钮推进各一）
- `tests/test_actuator.py`：`_swipe_path` 四方向、viewport_size 缺失回退、非法方向、
  **[e2e] 真浏览器 pointer 事件链**、**[e2e] touch 模式真的送到 TouchEvent**
- `tests/test_reader.py`：`box:null` vs 没看成、缺 `box` 键不可用、非法框丢弃、提示词排除项
- `tests/conftest.py`：假端点新增 `advance` / `advance_none` 两个模式
- 真机踩到：真浏览器里 `mouse.move(起点)` 会先发一次 `pointermove`（**在 `pointerdown` 之前**），
  断言拖动位移要从 `pointerdown` 之后再数

### 已知行为（不是 bug，需向用户说明）
真实站点跑完最后一题时会以 `advance_failed` 停下 —— 因为「最后一题」与「按钮没找到」
在无锚点页面上无法区分，宁可停也不静默收工。hint 里给了两个排查方向（换 touch / 换方向）。

## P14 末题判定（同日 · 用户实测反馈；**先出方案、用户确认后才施工**）

**用户原话**：「很多题目下一题安排在了滚动后的下一题，所以现在我需要加入一个程序来判断这是否是最后一题，
你可以先将你的方案我给我，等我确定后你在施工」。

我先做定点侦察（读 `_advance` 三段阶梯 / `_visual_fallback_enabled` 边界 / 靶场坑位），
然后给了方案并**只问了 4 个决策点**。用户的回答：

| 决策点 | 用户选择 |
|--------|---------|
| 判不出来（UNKNOWN）怎么办 | **暂停 + 引导卡让我一句话确认**（新增错误码 + 两个按钮） |
| 真实形态 | **两种都有**：向下滚就出现 / 下方就是下一题区块 |
| 能否给样本 | 可以给保存下来的 HTML / 截图（→ 先做不依赖样本的部分） |
| 是否加靶场坑位 | **加** |

### 1. 要解决的是一个二义性，两侧代价极不对称
「找不到『下一题』」既可能是**最后一题**、也可能是**还没滚到**，而它们在画面上长得一模一样。
把后者当前者 = **静默跳掉后面所有题**，且界面显示「已完成」——看起来完全正常。
所以输出刻意是**三值**，`unknown` **默认不收工**。

### 2. 推进阶梯从三段变四段
第 0 段**滚动探测**：`count() > 0` 升级为**四态**（absent / present_hidden / present_disabled /
present_enabled）→ 不可点就**有界向下滚**（默认 6 步）再重查 → 找到可点的就直接点掉。
细节：先试 `mouse.wheel`（虚拟列表只认它），不动再退回脚本滚动（**会找 `overflow:auto` 内层容器** ——
很多答题页滚 `window` 是滚不动的）；查找分**题目作用域 → 整页**两级（按钮跑到容器外是常见的一类「找不到」）。

**语义边界（最关键的一条）**：滚动探测**对两类站点都开**（只可能把按钮找出来）；
**末题判定只对无锚点站点做**。有锚点站点里 `selectors.next` 是权威契约，
「没有按钮 = 干净跑完」**不许动** —— 否则靶场跑批的收尾会从「跑完」变成「暂停」，那是破坏性的。

### 3. 判定器：证据链 + 纯函数融合
新增 `perception/end_probe.py`（只读、零模型）。证据优先级：**进度元数据** > 滚动后重查 >
终点文案∧无按钮 > 视觉三值 > 滚到底（仅辅证）。`fuse_verdict()` 是**纯函数**，所以所有分支可纯内存测。

两条刻意的保守规则：
- **进度矛盾不下结论**：页面写「共 3 题」而我们做到第 5 条 → `unknown`。
  **不许**用「已经做超了」反推「做完了」。
- **视觉说「没有下一题」必须 ∧ 已滚到底**才敢收工 —— 否则那正是「还没滚到」的样子。

⚠️ **默认进度正则刻意不含裸 `(\d+)/(\d+)`**：题干里的分数「3/3」会被读成「第 3 题，共 3 题」
→ 判成最后一题 → 静默跳题。另加两道防误报：`end_progress_max_total`（挡「2026/09」这类日期）+
`current ≤ total`。

### 4. 运行级人工决定：`run_flag` 信箱表
条目级确认走 `task_item.state`，但「这是不是最后一题」是**整条运行**的属性 —— 没有条目可挂。
硬塞进 `run.status` 会污染状态机；硬塞进某个条目的 state 是语义造假。所以新增
`run_flag(run_id, key, value, note, created_at)`，界面写、编排层**轮询读**（跨进程可靠）。
键名常量 `core.db.RUN_FLAG_LAST_QUESTION` **两边共用**（各写一份字面量会漂移，
症状是「点了按钮毫无反应」，最难查）。

与 `_await_human` 同构，含三条纪律：**按「恢复」≠ 同意**；**进入等待前先清信箱**
（旧答案不许延续到下一题，否则人工确认会变成永久开关）；**等待必须有超时**
（`end_decision_timeout_s` 默认 180s）—— 批处理/CLI 没有界面，无限等就是**死锁**（跑批脚本永不返回）。

新接口 `POST /api/tasks/{id}/last-question` 两条路径都要管用：编排层在等 → 写信箱立刻生效；
**已经超时收尾 → `last` 把运行补记成 `finished`**（不给这条，用户点了按钮毫无反应，
任务永远停在「已暂停·待介入」，比不做这个按钮还糟）。

### 5. 靶场新坑 `next_after_scroll`（21 → 22 题）
非末题：「下一题」被 1200px 占位推到首屏之外、**滚到才出现**；**末题：按钮永不出现** +
「已是最后一题」。加在题 `8`/`15`/`51` 上，`51` 在文件末尾 → 默认全量跑的最后一题走「永不出现」分支；
`?seq=8,15` 一次覆盖两条。**只推「下一题」，不动提交按钮**（一个坑只测一件事）。
坑位元数据三处同步：`quiz_runtime.js` / `gen_traps_md.py::TRAP_INFO` / `test_mock_site.py::KNOWN_TRAPS`。

### 6. 三处真缺陷（都是这一轮自己踩到的）
| 症状 | 根因 | 修法 |
|------|------|------|
| 末题判定**永远退化成「问人」**，日志只有 `'NoneType' object has no attribute 'get'` | **`page.evaluate` 返回 `null` 是合法的**，且这时**不抛异常、只给回 `None`**；直接 `.get()` 抛 AttributeError 把证据链打断 | 加归一化 `_mapping()`；给吞异常补 `exc_info=True`（没有堆栈的失败查不出是哪一步坏的） |
| 单测「绿/红」莫名其妙 | 测试替身用 `innerText` / `scrollY` 这类**通用字串**认自己的注入脚本，而 `_page_signature` 也用 `innerText`、执行层也用 `scrollX` → 把别人的脚本一起吞了 | 注入脚本打**唯一标记**，替身按标记分派 |
| 新坑把 `test_all_questions_are_read` 弄坏 | 该用例靠点「下一题」遍历题库，而新坑让按钮初始 `display:none`；**Playwright 只把「可见」元素滚进视口**，对 `display:none` 等多久都不会变可见 | 修**测试助手** `helpers.py::click_next`：先有界滚动再点（真实站点同理） |

另有两处**契约计数护栏**按设计更新：事件总数 **26 → 28**、建表数 **6 → 7**（多了 `run_flag`）。
还有一次**假失败**值得记：跑全量时我改了 `scripts/check_ui.py`，`test_health_exposes_boot_rev` 报
`boot_rev != code_rev` —— 那是**真断言**（`code_rev()` 哈希 `core/ui/target/act/perception/solve/adapters/scripts`
下的 `.py/.js/.html/.css`），不是 flaky。**跑测试期间别改那 8 个目录。**
